# Historical candle HTTP 403 investigation, 2026-10-14

## Finding

The user-run test retrieved an SBIN quote (exchange timestamp 2026-10-14T11:22:28+05:30,
price 946.90), then the historical endpoint returned HTTP 403. Authentication, current master
mapping and quote retrieval had therefore succeeded for that run. That timestamp belongs to
the quote; it is not an independently recorded timestamp of the failed HTTP request.

**The historical request was denied; the precise broker/gateway cause is unresolved.** No
endpoint, method, serialization, token-selection or date-window defect was found that explains
the 403. No authenticated request was made during this investigation. It would be dishonest to
claim that a diagnostic code change restores historical access.

**Confirmed code defect P8-076:** the dispatcher stopped at every non-200 status before inspecting
the error envelope. Offline reproduction with PermissionException, TokenException and
InputException all produced category `http`; response.json was never examined. This lost useful
diagnostics even when a broker explicitly identified the reason. Fix described below.

`requestHeaders`, `getMarketData`, `getCandleData`, `_routes`, and `smartExceptions.py`.
Also checked the [official historical API documentation](https://smartapi.angelone.in/docs).

The wrapper deliberately suppresses the SDK's IP discovery and constructor logging. Its local
and public IP fields remain loopback, with a zero MAC field. This differs from the SDK's default
machine discovery but is identical for quote and candle calls. The successful quote does not
prove historical access accepts those metadata values. No IP is discovered, guessed, spoofed,
or silently changed by this patch. No endpoint fallback, SDK upgrade, retries, alternate key,
User-Agent workaround or authentication-policy bypass was introduced.

Read-only local verification: `recent_session('2026-10-14')` returns **2026-10-13**;
one SBIN EQ bhavcopy row exists for that event date with knowledge_date <= 2026-10-14.
The request window is `2026-10-13 09:15` to `2026-10-13 15:30` IST, on a completed evidenced
session, with canonical minute formatting and a one-day span. This is within the documented
30-day maximum span for ONE_MINUTE. It is a valid intraday window, not an assertion that all
minute bars or every auction/post-close period must be present. Event-time and knowledge-time
semantics are unchanged. The conservative 4.1-second process spacing remains; it cannot describe
other applications sharing the account or source IP.

## Account/app verification required

The current [SmartAPI team reply on historical-data static-IP requirements](https://smartapi.angelone.in/smartapi/forum/topic/5671/asking-for-static-ip-for-getting-api-for-historical-data/3)
states that Angel applies static-IP requirements to all app types, including data access.
This differs from the older 2025 announcement that exempted non-order APIs. Treat the current
team reply as a reason to verify the account's actual policy, not proof that IP caused this 403.
No separate historical-data permission checkbox or paid entitlement requirement was established
from the reviewed official material. Do not invent one or assume trading permission is needed.

Verify privately in the SmartAPI portal, or ask Angel support to check:

1. The exact app corresponding to the environment's key is active, belongs to the intended
   account, and is entitled to call getCandleData for NSE equities. If it is a legacy app, ask
   whether a migration or re-enablement is required for historical access.
2. Whether this app requires a registered static public IPv4 address; whether the registered
   primary/secondary address matches the actual outbound address seen by Angel. Also ask whether
   historical requests validate the client-IP metadata fields. Praman currently uses loopback
   metadata; editing a header cannot replace source-IP registration.
3. Whether Angel's historical-data gateway applied an app/account/IP deny rule or rate-limit
   restriction despite the single paced request, and which rule rejected it. Ask them to inspect
   their telemetry rather than recommend rapid retries.

Support case facts: successful login/quote, failing endpoint and POST method, HTTP 403, NSE/SBIN,
ONE_MINUTE, completed date/window above, and smartapi-python 1.5.5. The next manual run prints the
actual selected date/window and sanitized category. Do not send raw responses, request headers,
JWTs, refresh tokens, API keys, PINs or TOTPs. Use the authenticated support account to identify
the account. This agent has not contacted support or changed any portal setting.

There are first-hand reports on the official support forum of a historical gateway returning

## Offline changes

- `desk/angel_market_data.py`: examine error envelopes for REST 4xx responses in memory. Exact
  SDK PermissionException/TokenException/InputException indicators map to fixed permission,
  authentication or request-validation categories. Selected exact broker codes map to fixed
  authentication, date-format or rate-limit categories. Unknown or conflicting evidence remains
  unclassified; HTTP 403 never becomes success, even with a success-shaped body. HTTP 200 error
  envelopes are also rejected. HTTP status is preserved; no raw code/message is exposed.
- Local invalid/current/future candle dates have a separate `candle_date` category and fail before
  network access. Broker date-format rejection is distinct (`broker_date`), based on AB13000,
  corroborated by the [SmartAPI team's date-format response](https://smartapi.angelone.in/smartapi/forum/topic/4596/ab13000-error-extracting-historical-data).
- HTTP 429, exact AB1021, or an exact known non-JSON gateway rate-limit indicator are classified
  as **server reports rate limiting**, not as proof of client quota abuse. An HTML page or a body
  merely containing similar words is not enough. No retry follows any classification.
- `scripts/angel_connection_test.py`: candle failures print the canonical selected date/window;
  ambiguous access denials point to app/static-IP verification. No extra authenticated calls.
- `tests/test_angel_candle_403.py`: SDK wire-contract comparison, each rejection class, secret
  non-disclosure, malformed/unknown responses, no retries, no accidental success on 403,
  local date rejection, and smoke-test logout/no-stream behavior.
- `tests/test_angel_diagnostics.py`: HTTP 429 now expects the more specific rate-limit category.
  Public master parsing/error policy is otherwise unchanged, as are quote/login request formats.

`PermissionException` only confirms that the broker reported a permission denial; it cannot
identify which portal setting or policy is responsible. Generic 403 intentionally says
`Access denied; cause unclassified`. No response body is logged, persisted or included in the
exception, and no raw headers, authentication URLs or exception strings are exposed.
